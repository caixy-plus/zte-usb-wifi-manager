# 阶段 1–2 连续交付设计

## 1. 目标与范围

本轮连续完成：

1. 阶段 1：把现有只读总览扩展为有真实数据契约的移动网络、Wi‑Fi/终端、流量、
   短信元数据、电池、设备、诊断和日志页面。
2. 阶段 2：建立统一的安全动作框架，并逐项接入经过 U25S 固件校准的 SIM、APN、
   连接模式、Wi‑Fi、流量计划和短信写操作。

阶段 3 的 TR3000 USB 供电控制、充电日程和自动断电不进入本轮。恢复出厂、关机、
固件更新、修改 IMEI 和射频隐藏参数也不开放。

## 2. 交付顺序

采用纵向切片，每个切片同时完成厂商字段、规范化模型、快照、rpcd、LuCI 和测试：

1. 扩充基础快照和能力模型。
2. 移动网络与 SIM。
3. Wi‑Fi 与接入终端。
4. 流量统计与流量计划。
5. 短信元数据、按需正文和短信动作。
6. 电池、设备、诊断和脱敏事件日志。
7. 通用动作队列。
8. 逐项校准并开放阶段 2 写操作。

一个切片未通过自动化测试和能力门控检查前，不开始开放该切片的写按钮。

## 3. 架构

保持单向数据流：

```text
LuCI → rpcd/ubus → 原子动作请求目录 → daemon → U25S adapter
LuCI ← rpcd/ubus ← 原子状态快照     ← daemon ← U25S/netifd
```

- daemon 是唯一可以访问 U25S 的进程。
- rpcd 读取缓存快照；写方法只校验请求并原子投递动作，不直接访问设备。
- daemon 串行消费动作，一次只运行一个会改变 U25S 状态的操作。
- 动作结果写入快照，LuCI 按 `operation_id` 轮询状态。
- 短信正文只在用户点开单条消息时通过独立缓存返回，不进入常驻总览快照或日志。

运行时文件位于 `/var/run/zte-usb-wifi-manager/`：

```text
status.json
actions/pending/<operation_id>.json
actions/running/<operation_id>.json
actions/results/<operation_id>.json
events.jsonl
sms/<message_id>.json
```

目录由 root 创建，模式为 `0700`；文件使用临时文件加原子重命名，模式为 `0600`。

## 4. 阶段 1 数据契约

顶层快照保留现有字段，并扩展为：

```json
{
  "device": {
    "model": "U25S",
    "modem_state": "ready",
    "cellular": {},
    "sim": {},
    "wifi": {},
    "traffic": {},
    "sms": {},
    "battery": {},
    "system": {}
  },
  "network": {},
  "operation": null,
  "events": [],
  "updated": 0
}
```

字段规则：

- 缺失值使用 `null`，不使用静态示例或猜测值。
- `sim.active_slot_raw` 保留厂商原始值；完成卡槽校准后才额外输出语义
  `active_slot`。
- 流量值统一为非负整数 byte，速率统一为 byte/s。
- Wi‑Fi 客户端只输出显示名、连接类型和脱敏后的稳定会话 ID；MAC 地址不写日志。
- 常驻快照只包含短信数量和未读数，不包含号码和正文。
- 系统信息只包含 UI 所需的型号、固件版本、运行时间和能力状态，不暴露设备唯一标识。

LuCI 的十个标签都必须有真实组件和切换逻辑。没有数据时显示“不可用”及原因，而不是
空白页；后台错误和陈旧快照继续显示显式警告。

## 5. 阶段 2 安全动作框架

rpcd 新增语义化方法：

- `operation_status`
- `cellular_action`
- `wifi_action`
- `traffic_action`
- `sms_list`
- `sms_get`
- `sms_action`
- `logs`

每个写请求必须依次通过：

1. LuCI 会话 ACL。
2. 严格 JSON 参数校验和固定枚举转换。
3. UCI `write_enabled=1`。
4. 对应操作能力标志为 `true`。
5. 当前固件 profile 与校准记录完全匹配。
6. 没有冲突动作正在执行。

`write_enabled=1` 不能绕过能力标志或固件校准。生产 profile 未校准时返回结构化
`unsupported`，模拟器 profile 可以显式开放测试能力。

动作状态为：

```text
queued → running → verifying → succeeded
                           ↘ failed
                           ↘ timed_out
```

危险动作不盲目重试。请求超时后先读取设备状态；只有读回结果能证明目标状态已达到时
才标记成功，否则标记 `timed_out` 并停止。

## 6. 设备动作

### 6.1 SIM

前端只提交 `sim1` 或 `sim2`。adapter profile 将语义卡槽转换为已校准的
`card_index`。切换后依次验证活动卡槽、SIM 就绪、注册状态和 PPP 恢复；超时不得
在两个卡槽间循环切换。

### 6.2 APN 与连接模式

APN 名称、认证方式、用户名和密码分别校验；密码不回填、不记录。连接模式只接受
profile 声明的枚举。保存后读回当前配置，字段一致才成功。

### 6.3 Wi‑Fi

分别控制主 Wi‑Fi 开关、频段和主 SSID。SSID、密码、信道和加密方式使用独立校验器。
修改可能中断 U25S 自身 Wi‑Fi 时，确认框必须说明不影响 OpenWrt LAN，但可能断开直连
U25S 的客户端。

### 6.4 流量计划

只允许配置计费周期、总量和告警阈值。流量清零单独作为危险动作，需要二次确认并在
操作后验证计数器。

### 6.5 短信

列表只返回分页元数据；正文按 ID 读取并存放于短期缓存。发送、删除和标记已读是独立
动作。号码、正文、短信 ID 映射和厂商响应不得进入事件日志或仓库 fixture。

## 7. 校准与能力开放

每个生产写能力按同一流程开放：

1. 从当前固件原生页面确认功能存在。
2. 在 U25S API 模拟器加入正常、拒绝、超时和会话过期场景。
3. 使用脱敏请求/响应 fixture 固化参数名称、编码和成功条件。
4. 在真实 U25S 上执行一次受控动作和一次失败路径验证。
5. 校验操作后读回、超时行为及对 PPP/Wi‑Fi 的副作用。
6. 将固件 profile 的单项能力设为 `true`。

未完成第 4–5 步时可以合并框架和模拟器代码，但 Release 中对应生产能力必须保持
`false`。

## 8. 错误处理与日志

- 认证过期只自动重新登录一次。
- 写动作进行时暂停冲突动作，不暂停只读轮询。
- daemon 重启后扫描 `running` 动作，统一转入 `verifying`，通过读回决定结果。
- 动作结果保留有限条目并按时间清理，不写入闪存。
- 事件日志只记录动作类型、阶段、结果、耗时和脱敏错误码。
- 密码、Cookie、认证摘要、号码、短信正文、IMEI、IMSI、ICCID 和完整 MAC 禁止出现。

## 9. 测试

- POSIX Shell 单元测试覆盖字段规范化、参数校验、冲突矩阵和动作状态转换。
- U25S API 模拟器覆盖读取、每种写动作、会话过期、超时、拒绝和错误 JSON。
- rpcd 行为测试真实调用 `list/call`，验证 ACL、错误结构和原子动作投递。
- LuCI Node 测试覆盖十个标签、轮询、表单校验、确认框、操作状态和错误横幅。
- Playwright 在本地 LuCI fixture 页面验证标签切换、移动端布局和前后端契约。
- OpenWrt 25.12.5/24.10.7 QEMU 验证安装、procd、rpcd/ubus、升级和卸载。
- 真实 U25S 校准只在明确的单项用例中临时开放写接口；不以主路由器做探索性测试。

## 10. 完成标准

阶段 1 完成：

- 十个标签都有真实数据契约和可工作的页面。
- 读取失败、缺字段和陈旧状态有明确展示。
- 常驻状态和日志不含敏感信息。

阶段 2 完成：

- 通用动作队列、冲突控制、超时读回和脱敏事件日志通过测试。
- SIM、APN、连接模式、Wi‑Fi、流量计划和短信均完成模拟器行为测试。
- 只有完成真实固件校准的单项能力在生产 profile 中开放。
- 所有开放动作都通过成功、失败和操作后验证用例。
- 两个受支持 OpenWrt 版本的 QEMU 安装和回归测试通过。
